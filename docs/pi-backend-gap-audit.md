## Scope, evidence, and interpretation

Audit only: no production changes, backend calls, credential operations, model requests, or fixes were performed by this audit. The only deliverable is this document. This is a **source audit**, not a new end-to-end qualification. The existing successful text-chat POC is consistent with the code; it is not evidence that the rest of OpenGhost works.

- Repository: OpenGhost, branch `cpp-native-extraction`, HEAD `a6e15f7c657b60b25a9734af233d1718aef1ee18`.
- Scope: **working-tree C++/QML**, including uncommitted Pi work, not just HEAD and not the frozen JavaScript reference. `README.md`, `docs/cpp-port.md`, and parts of the earlier browser audit predate the POC/browser automation and are not authoritative about current wiring.
- Pi inspected: installed `@earendil-works/pi-coding-agent` **1.0.4**, under `/home/brian/.bun/install/global/node_modules/@earendil-works/pi-coding-agent/`. `pi` resolves to its `dist/bundle/cli.js`. Exact commands were checked against `dist/modes/rpc/rpc-types.d.ts` and `rpc-mode.js`, not inferred from TUI commands.
- Other production files were being changed concurrently during this audit. The initial dirty files were `src/backend/pi_backend.{cpp,h}` and `src/backend/pi/`; subsequent external changes added auth-step plumbing to `types.h`, `chat_service.{cpp,h}`, and `window.cpp`, then resource packaging in `CMakeLists.txt`, bridge loading and `set_model` dispatch in P. The matrix reflects those later changes, not the earlier text-only POC. The final snapshot/evidence note below identifies the audited state. **Those changes are not audit edits.**
- Normal launch still selects no backend. Andrew must use **`openghost-cpp --pi`**; `--fake-backend` is a separate fixture and wins if both flags are supplied. The matrix's test impact assumes `--pi`, a working Pi executable, and separately configured Pi credentials unless it specifically tests authentication.

A feature is counted once per numbered matrix row. Related suboperations are listed inside the row. The separate absence inventory is **not** counted as shipped functionality. In particular, a C++ enum, a test fixture, or a hidden QML component is not evidence of an exposed, working feature.

### Status definitions

1. **FRONTEND ONLY** — the precisely scoped function is implemented locally; no Pi behavior is needed. This does not certify pixel parity, every OS, or unrelated persistence guarantees.
2. **PI ALREADY WIRED** — the narrow function actually crosses the current Pi adapter and has a usable path. This is not a claim that the encompassing workflow is complete.
3. **PI SUPPORTS, NOT WIRED** — the needed Pi functionality exists, but this UI has no effective connection. The support column explicitly distinguishes stock RPC from SDK/extension-only support.
4. **PARTIAL** — pieces exist, but important behavior, semantics, or integration is incomplete.
5. **MISSING FROM PI/RPC** — no stock RPC operation/contract implements the requirement. SDK building blocks may make a bridge possible; this is not necessarily a request to change upstream Pi.
6. **DEAD/PLACEHOLDER** — presented or reachable functionality has no operational implementation. Where relevant, the support column also records whether Pi could supply part of it.

## Existing Pi POC: exact implemented boundary

The inspected POC is a direct `QProcess` adapter, not an implementation of `ByteTransport`. `CMakeLists.txt` links `src/backend/pi_backend.cpp`; `src/main.cpp` chooses it only with `--pi`. Since M04–M08 it runs one Pi child per chat session plus a control child; `src/backend/pi_process.{cpp,h}` (`PiProcess`) owns each child's framing, RPC correlation and bridge commands.

### Actual command/event mapping

| OpenGhost semantic operation | Current POC behavior |
| --- | --- |
| Initialize | Copies the Qt-resource bridge to a temporary directory and starts a `pi --mode rpc --no-session -e <bridge>` control child for catalog, providers and sign-in. Chat children start on demand: `pi --mode rpc --session <AppData>/pi-sessions/<hex id>.jsonl -e <bridge>` in the chat's folder. Every child's bridge is verified with `get_commands` before bridge calls are released. Returns auth, session-recovery and session-delete capabilities. Missing bridge makes ProvidersList fail and prevents C from becoming ready. |
| ModelsList | Control child's `get_available_models`, with the model its `get_state` names (Pi's default) moved first; failure reaches caller. |
| ProvidersList | Sends bridge `providers`; maps real Pi provider methods and configured/stored flags. Four reference providers sorted first, not fabricated rows. |
| SetKey/Login/AnswerLogin/CancelLogin/Logout | Bridge `setKey/login/answer/cancel/logout`; token-correlated terminal results and auth steps; Pi owns credentials. Auth completion triggers catalog refresh. |
| StartTurn | Deduplicates by `(session, clientTurnId)` (journal, then Pi's turn records); one turn per chat; checks create-only/version against the chat's recorded incarnation. | GetSession | Missing unless Pi has the chat's session. Returns its incarnation, sequence and exactly the requested accepted client turn (or the running one): from the in-process journal, else rebuilt from Pi's session entries (27). Never a turn Pi did not take. |

| RetryTurn | The named failed turn, while still Pi's latest, through bridge `{op:"retry"}` (05). |

### Auth bridge work present in the working tree

The separate, uncommitted `src/backend/pi/openghost-bridge.js` registers `/openghost`. Its current implementation has `providers`, `login`, `setKey`, `answer`, `cancel`, `logout`, using the session's `ctx.modelRegistry.runtime` and Pi-owned credential storage. It emits JSON payloads through RPC `setStatus` records:

- `openghost:<token>`: terminal result;
- `openghost:<token>:event`: auth URL/device-code/info/progress;
- `openghost:<token>:prompt`: prompt ID, type/options/placeholder.

It includes per-provider AbortControllers, prompt promises and `SettingsManager.getOrCreateDeviceId` for OAuth. `LoginStep`/`AnswerLogin` are projected by C/W into the existing provider form. **The final adapter snapshot does load `-e`, verify the command's source, parse status tokens, forward steps/answers and invoke real auth operations.** CMake embeds the JavaScript as a Qt resource; it executes in the Pi child, not as a native/UI runtime. Earlier readings before these concurrent edits showed an unloaded file; that is no longer the audited state. The bridge is OpenGhost-specific extension work, not evidence upstream RPC gained auth commands. Auth races, cancellation, storage failure, and real provider success were not tested by this audit.

**M14 addition:** the bridge now also has `retry`. It requires an idle Pi whose latest branch message is a failed assistant reply, then starts a continuation with a hidden `openghost-retry` custom message. Its `context` handler removes each trigger, plus the failed replies the trigger retries, from every model request.

### Important semantic details for any later integration

- **Message/run identity:** Pi's wire stream generally has no OpenGhost session/turn/client/message IDs. Stock RPC controls one active session; an OpenGhost turn can encompass many Pi assistant turns/tool batches/retries. Only `agent_settled`, not each `agent_end` or `turn_end`, is the final automatic-work boundary. Persist real mappings rather than claiming locally generated IDs describe a durable Pi journal.
- **Input dispositions:** `handled` means the input was consumed without necessarily starting an agent run. `queued` means queued, not applied. A successful command response is not completion. Extension-generated work can be independent of the submitted command.
- **Usage units:** OpenGhost's `Usage.input` includes cached input (`cached <= input`) and its totals are `input + output`; Pi separates `input`, `cacheRead`, `cacheWrite`. For the normal Pi categories map OpenGhost input to **`input + cacheRead + cacheWrite`**, cached to `cacheRead`, written to `cacheWrite`, output to `output`; don't add Pi reasoning again (already in output). `message_update.usage` is cumulative per response, so forwarding each snapshot as an increment overcounts. Final message usage, tools and compaction must not be charged again from cumulative `get_session_stats`. Use actual assistant model/provider, not the possibly stale picker label. Session totals can include idle/cache-warm or summary work not tied to a foreground reply: current C requires a correlated turn/message before charging, so blindly manufacturing that ownership is also wrong.
- **Context is not lifetime tokens:** use `get_session_stats.contextUsage` and honor null tokens after compaction. OpenGhost has no visible billing balance or context-meter control; do not fabricate one or confuse usage with account limits.
- **Auth is not model availability or site cookies:** model catalog availability is configured access, not validated login. Stored-key removal may leave environment/config access. Never import browser sign-in hints as Pi credentials. The auth bridge must not use ordinary logged prompt traces for secrets or save them in chat history.
- **Tools and safety:** Pi can execute even when OpenGhost has no tool cards. Pi's own security documentation explicitly says it does not request approval before every tool call and uses process permissions. Enforcing OpenGhost modes must happen before effects, not when a result arrives.
- **Browser cancellation is not rollback:** native tools already guard page/ref/read/job identities and return explicit error/cancel/handed-back results. Preserve them; screenshots and downloads are real effects, not retryable display operations. C currently refuses host calls before it has the matching accepted turn identity; the Pi bridge must order/buffer correctly.
